# Nokia 3230 bring-up — prep and run plan

Not run yet. Written for the retired `s60v2-3230-experiments` branch; the
firmware it needs is now on master (see "Firmware" below). Read
`S60V2-FINDINGS.md` first — most of what could go wrong has already been
diagnosed on the 7610, and the point of this run is partly to use the 3230 as
a **control** for what was learned there.

**Read the 2026-10-31 update first.** It found that gnubox v1.1 writes
`TSYName = PHONETSY` for every mode, so the dial needs the network to accept
a real CSD call. If the 3230's gnubox build does the same (check its CommDB
`ModemBearer` record), expect the same 2-3 s "network problem" on any SIM
without CSD, whatever the bridge advertises. The cheapest first check is
therefore the `TSYName` in the 3230's dump, then which `.tsy` files it ships.

## Why a second handset

The 7610 gets as far as a fully open RFCOMM channel and then sends zero user
data before hanging up at ~6 s. The stall is above RFCOMM, in the phone's
telephony/agent layer, and the surviving hypothesis is that Symbian's CSD
agent cannot complete its pre-call without GSM registration.

The 3230 tests whether that is handset-specific.

**But be careful what it can prove.** If the 3230 fails identically, that
shows the failure is *not* specific to the 7610 — it does not by itself prove
the 2G theory, because both phones may share the same SIM or the same
no-coverage location. To make this a real control rather than a repeat, record
at dial time:

- whether the 3230 shows a carrier name and signal bars on screen
- which SIM is in it, and whether it is the same one the 7610 used
- whether it registered on 2G at all (`Settings → Phone → Network`)

Without those three, an identical failure is only weak evidence.

## Unknown to resolve first: which Feature Pack

This matters more than it looks. gnubox defines `NOBTREGISTRY` only for
`__S60ED2FP2__` (`gnuboxPhone.h:58-60`), and that flag switches where the
BTCOMM::5 port config is stored:

- **FP1** (what the 7610 is) → `CBTRegistry::SetDefaultCommPort`, i.e. the
  phone's Bluetooth registry. Invisible in `commsdb.txt`. This is exactly why
  the 7610's security setting could never be verified from the phone side.
- **FP2** → gnubox writes the **BTDefault table in CommsDB** instead, so the
  stored device address and `DefaultSecurityLevel` **do** show up in the dump.

So if the 3230 is FP2, the dump gives us the one thing the 7610 hid. Don't
assume either way — two cheap checks answer it:

1. `*#0000#` on the phone, or `Settings → Phone → Phone info`, for the
   software version.
2. The first CommsDB dump: does it contain a `BTDefault` /
   `BTSecurityDevice` section? If yes, FP2 path; if not, FP1 path.

## Phone-side prep

1. **Back up the phone.** gnubox rewrites CommsDB and cannot restore it from
   its own dump.
2. Create `c:\logs\gnubox` on the phone **before** running gnubox for the
   first time — the log only appears if the folder already exists, and it is
   the thing that would have answered the 7610's open question.
3. Create an internet access point named exactly **`Bt`** (case matters):
   - bearer **Data call** (a.k.a. CSD / Dial-up — *not* GPRS)
   - number to call: something undiallable, e.g. `321`
4. Install **`gnubox-3230.sis`**.
5. Launch gnubox. The `DialOutISP` record and the number should show;
   `ModemBearer` will still read `No rec`.
6. `Options → Install → Create records`.
7. `Options → Exit` (not just task-switch), then relaunch. `ModemBearer`
   should now be present and the `No rec` error gone.
8. `Options → Debug → Dump Full CommsDB` → save `c:\nokia\commsdb.txt` off
   the phone. This is the baseline to diff every later change against, and it
   answers the FP1/FP2 question above.
9. Set the RAS login script if following the Schuon tutorial route
   (`Options → Install → set RAS login script`).

## Firmware

Plain master, nothing to rebuild:

- **All three service classes advertised**: LAP 0x1102 (ch 3), SPP 0x1101
  (ch 4) and DUN 0x1103, which shares ch 4 with SPP so no third RFCOMM
  service is needed. gnubox's 2box menu searches a different UUID per option
  (Serial → 0x1101, LANAccess → 0x1102, Dialup → 0x1103), so every option can
  be tried without a reflash.
- **mRouter bootstrap on.** After the first pairing it SDP-browses the phone
  and logs every RFCOMM service the phone exposes, then connects into the
  first SPP/DUN one.
- **Debug switches on `/debug`**: tick *HCI packet trace* and *Verbose bridge
  events* before pairing (they survive the reboot). Verbose adds the
  link-security line at RFCOMM open.

```bash
python -m serial.tools.miniterm /dev/ttyUSB0 115200 | tee /tmp/3230-run1.log
```

## Run order

1. Pair from the phone (PIN `0000`). Capture the bootstrap's
   `[SDP] phone service: ch N name '...'` lines — that is the service
   inventory. If it instead logs `phone exposes none of the known
   modem/COM-port service classes`, the 3230 is like the 7610 and
   `2box → Auto` cannot work on it either.
2. gnubox → `2box → Direct over BT/Serial`, select **Vetera Bridge**, and at
   "Do you want to require encryption?" press the **LEFT** soft key. Only the
   left key reaches `SetEncryption()`; the right key is rendered unlabelled on
   these phones and silently gives authentication-only.
3. Dial via `Options → Debug → bring IF up` — better error feedback than
   Opera. Record the exact text of any Symbian error note.
4. If that stalls, try `2box → Direct over BT/LANAcc` and
   `→ Dialup` — no reflash needed now that all three records are advertised.

## What to look for in the log

- `[SDP] phone service:` — the phone's own service inventory (step 1 only).
- Which UUID the phone searches for at dial time, and which channel it opens.
- `link security: level=… authenticated=… key_size=…` — read `level` and
  `key_size`; `authenticated` reads false for legacy PIN-paired links
  regardless of truth (see the comment at that log site).
- **Any user data at all from the phone** after the channel opens. That is the
  pass condition. The 7610 never produced a single byte.
- Time from channel open to `DISC`. The 7610's was 5.99 s, every time; a
  materially different timeout points somewhere new.
